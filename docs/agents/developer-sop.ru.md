## 📁 Обновление документации

**Правило:** После каждого успешно завершённого Issue, который меняет архитектуру, API, схему БД, пайплайн данных или операционное поведение, разработчик ОБЯЗАН обновить документацию проекта в `docs/`.

**Матрица обновления документации:**

| Изменение в Issue | Документы для обновления |
| --- | --- |
| Новый модуль/файл | `docs/project-context.md` §2 (File Structure) |
| Добавлен/изменён API-эндпоинт | `docs/project-context.md` §5 (API Endpoints) |
| Изменение схемы БД | `docs/project-context.md` §3 (Database Schema) |
| Изменение пайплайна данных | `docs/project-context.md` §4 + `docs/handover.md` §4 |
| Новый операционный gotcha | `docs/handover.md` §10 (Operational Gotchas) |
| Изменение статуса roadmap | `docs/project-context.md` §8 (Roadmap Status) |
| Изменение стратегии | `docs/strategy/*.md` |

**Правила:**
- Держи ОБЕ языковые версии синхронными: `*.md` (EN) и `*.ru.md` (RU).
- Обновляй заголовок `Last refreshed: <date> (task-NNN)` в каждом изменённом документе.
- Обновление документации входит в ТОТ ЖЕ PR (или в follow-up PR, привязанный к тому же Issue).
- Ссылайся вместо дублирования (handover.md ссылается на секции project-context.md).

## 📂 Артефакты задачи (reports/)

**Правило:** При решении ЛЮБОЙ Issue создаётся рабочая папка внутри `reports/`.

**Именование папки:** `<NNN>-<branch-name>`, где:
- `<NNN>` — номер Issue (с ведущими нулями для сортировки, например `042`),
- `<branch-name>` — имя созданной ветки без префикса `feature/` (например `issue-42-fix-evaluator`).

Пример: `reports/042-issue-42-fix-evaluator/`.

**Назначение:** единообразная сортировка по номеру Issue и однозначная привязка артефактов к ветке.

### Обязательные артефакты задачи (создаются один раз на Issue)

| Файл | Назначение |
| --- | --- |
| `issue-context.md` | Живой документ по задаче. Ведётся от начала до конца. Содержит: план выполнения, отметки о выполненных шагах, что сделано, что осталось, принятые решения и отклонения от плана. |
| `report.md` | Итоговый отчёт по Issue (для PR-комментария). |

### Обязательные артефакты bash-скрипта (создаются заново на КАЖДОМ скрипте)

| Файл | Назначение |
| --- | --- |
| `log.txt` | Сырой лог выполнения текущего bash-скрипта (команды, stdout/stderr, коды возврата). **Перезаписывается** на каждом новом скрипте. |
| `context.md` | Человекочитаемая выжимка собранного контекста. Обязателен, если скрипт выполняет сбор контекста. |

### Свободные артефакты

- Максимум 2 свободных файла на один bash-скрипт (на усмотрение агента): например, `patch.diff`, `test-output.txt`, `regression.json`.
- Все имена файлов — латиница, без пробелов.

### Лимит файлов на один bash-скрипт

**Правило:** В ходе выполнения ОДНОГО bash-скрипта разрешено создавать **максимум 5 файлов**.

**Обоснование:** агент способен осмысленно прочитать не более пяти файлов за один проход. Превышение лимита означает, что скрипт делает слишком много и должен быть разбит на несколько последовательных bash-скриптов.

По итогу работы над Issue в папке может накопиться больше пяти файлов — это нормально, если каждый отдельный bash-скрипт не превышал лимит.

**Важно:** папка `reports/` находится в `.gitignore`. Артефакты НЕ коммитятся в репозиторий. Они передаются через комментарии к PR, а не через структуру репозитория.

## 🔄 Алгоритм задачи

### Шаг 1. Анализ задачи

1. Открой `https://github.com/svyaziment/trading-terminal/issues/<N>`
2. Изучи описание, критерии приёмки, связанные файлы.
3. Если неясно — перейди в режим обсуждения в комментариях к Issue. НЕ пиши код.
4. Зафиксируй `short-description` для будущего имени ветки и папки артефактов. Формат: `issue-<N>-<short-description>` (латиница, дефисы, без пробелов).
5. Создай папку артефактов задачи: `reports/<NNN>-issue-<N>-<short-description>/`, где `<NNN>` — номер Issue с ведущими нулями. Папка создаётся до ветки, потому что её имя выводится из `short-description`, зафиксированного на этом шаге, а не из факта существования ветки.

Пример для Issue #42 с описанием «fix evaluator»:
```
reports/042-issue-42-fix-evaluator/
```

### Шаг 2. Создание и публикация ветки

```bash
git checkout main
git pull origin main
git checkout -b feature/issue-<N>-<short-description>
git push -u origin feature/issue-<N>-<short-description>
```

Имя ветки должно совпадать с `short-description`, зафиксированным на Шаге 1. После создания ветки создай в папке артефактов `issue-context.md` с черновым планом (детализируется на Шаге 3.5).

### Шаг 3. Сбор контекста (ОБЯЗАТЕЛЬНО для ЛЮБОЙ задачи)

**Правило:** Сбор контекста обязателен ПЕРЕД началом выполнения любой задачи — без исключений. Угадывать запрещено.

**Как собирается контекст:**

1. Контекст собирается **чтением и записью необходимых файлов через bash-скрипт** (см. `docs/refresh/context_collector.py` как референс). Ручной осмотр файлов «глазами» не заменяет скриптовый сбор — нужен воспроизводимый артефакт.
2. Скрипт обязан начинаться с:
   ```bash
   export MSYS_NO_PATHCONV=1
   export MSYS2_ARG_CONV_EXCL="*"
   ```
3. Результат сохраняется в `<reports-dir>/context.md` — человекочитаемая выжимка собранного контекста. Это единственный обязательный формат; машинный `.json` не используется.
4. `log.txt` в `<reports-dir>/` перезаписывается логом этого скрипта.

Пример:
```bash
export MSYS_NO_PATHCONV=1
export MSYS2_ARG_CONV_EXCL="*"
ISSUE_N=42
BRANCH="issue-42-fix-evaluator"
REPORTS_DIR="reports/$(printf '%03d' ${ISSUE_N})-${BRANCH}"
mkdir -p "${REPORTS_DIR}"

python docs/refresh/context_collector.py \
  --task-id "task-${ISSUE_N}-context" \
  --files backend/app/analytics/target_file.py,backend/app/api/target_api.py \
  --tables target_table_1,target_table_2 \
  --output "${REPORTS_DIR}/context.md"
```

### Шаг 3.5. Декомпозиция задачи (ОБЯЗАТЕЛЬНО)
- **Оформление скрипта — только файл `.sh`**: тело bash-скрипта создаётся в файле `scripts/<NNN>-<issue-name>.sh` через heredoc (`cat > scripts/<NNN>-<issue-name>.sh <<'TASK_EOF' … TASK_EOF`), затем `chmod +x scripts/<NNN>-<issue-name>.sh` и запуск `bash scripts/<NNN>-<issue-name>.sh`. Вставка тела скрипта напрямую в интерактивный терминал запрещена: большие вставки крашат сессию Git Bash (потеря блоков, обрыв сессии). Результат проверяется чтением файлов (`cat reports/<NNN>-<issue-name>/…`), а не наблюдением вывода вставки.
- **Файлы логирования — только `.txt`**: все логи задачи и прогонов пишутся с расширением `.txt` (`log.txt`, `run_v4.txt`, `shards.txt`); расширение `.log` для файлов логирования не используется.

**Правило:** После сбора контекста разработчик ОБЯЗАН выработать план выполнения Issue и разбить его на необходимое количество шагов.

**Требования к плану:**

- План сохраняется в `<reports-dir>/issue-context.md` в разделе «## План выполнения».
- Каждый шаг — атомарная операция с проверяемым результатом (патч, пересборка, тест, обновление доки).
- **Запрещено пытаться выполнить всю задачу за один шаг.** Если задача многосоставная — она режется на N шагов, каждый из которых исполняется и логируется отдельно.
- Если в ходе выполнения выясняется, что шагов нужно больше — план дополняется, `issue-context.md` обновляется.

**Правило ведения `issue-context.md`:**

- `issue-context.md` — живой документ. Он обновляется **после каждого выполненного шага**, а не только в конце задачи.
- После шага проставляется `[x]` в плане и добавляется запись в раздел «## Журнал изменений»: что сделано, какие файлы затронуты, какие решения приняты, какие отклонения от плана.
- Если шаг отменён или переделан — это тоже фиксируется.
- На момент завершения задачи `issue-context.md` должен однозначно отвечать: что по плану сделано, что осталось, почему.

**Формат `issue-context.md`:**

```markdown
# Issue #<N>: <краткое название>

## План выполнения
- [ ] Шаг 1. <описание> → ожидаемый артефакт
- [ ] Шаг 2. <описание> → ожидаемый артефакт
- [ ] ...

## Журнал изменений

### Шаг 1. <описание> — <дата/время>
- Статус: выполнено
- Изменённые файлы: `path/to/file.py`
- Решения: <почему сделано именно так>
- Отклонения от плана: <если были>

### Шаг 2. ...
```

### Шаг 4. Создание скрипта решения

- Начинай с `export MSYS_NO_PATHCONV=1` и `export MSYS2_ARG_CONV_EXCL="*"`.
- Используй heredoc в кавычках (`<<'PYEOF'`) для кода.
- Атомарные патчи: проверяй, что каждый regex-якорь находит РОВНО 1 совпадение до применения. Если 0 или >1 — прервись с `PATCH_FAIL`.
- После создания/изменения файла: `wc -c path/to/file`.
- После изменений backend: `docker compose up -d --build backend`.
- **Один bash-скрипт — одна смысловая операция.** Если скрипт делает больше одной операции (например, и патчит, и пересобирает, и тестирует) — разбей его на последовательные bash-скрипты.
- **В рамках одного bash-скрипта создаётся максимум 5 файлов** (см. раздел «📂 Артефакты задачи»). Превышение означает, что скрипт делает слишком много.
- `log.txt` перезаписывается на каждом новом bash-скрипте.
- После выполнения скрипта обнови `issue-context.md` (см. Шаг 3.5).

### Шаг 5. Обновление документации

После завершения Issue обнови документацию проекта в `docs/` согласно матрице обновления документации выше. Обе языковые версии (EN и RU) должны быть обновлены.

## ⏳ Длительные прогоны и тяжёлые тесты: только detached-режим с воркерами и проверкой живости
Правило: любой прогон с ожидаемой длительностью больше 10 минут (гейты паритета, аналитические
extract'ы, портфельные прогоны, регрессионные матрицы, тяжёлые тесты) выполняется ТОЛЬКО detached,
возобновляемо и наблюдаемо. Attached-запуск для таких задач запрещён.
Обязательные атрибуты прогона:
- Запуск: `nohup python <script> >> <reports-dir>/log.txt 2>&1 &`, PID сохраняется в
  `<reports-dir>/run.pid`. Защита от повторного запуска: если старый PID жив (`kill -0`),
  новый запуск аварийно завершается с ABORT.
- Возобновляемость: кэш по единицам работы (тикер/книга/стадия) в gitignored-каталоге (`cache/...`);
  рестарт продолжает с кэша, а не с нуля.
- Параллелизм: `ProcessPoolExecutor` с явным `--workers N`; N выбирается по окружению предыдущих
  прогонов (например `environment.workers` в summary.json); при ошибках пулов/соединений БД —
  уменьшить N и перезапустить (кэш сохраняет прогресс).
- Наблюдаемость: прогресс-логи с flush по каждой единице (`[book] [k/N] <ticker> ok ...`);
  код выхода пайплайна берётся через `${PIPESTATUS[0]}`, а не `$?` после `| tee`.
- Воркеры сами инициализируют свои process-local глобалы (реестр плагинов стратегий, логирование):
  на Windows spawn глобалы родителя не наследуются (урок #147: без `register_default_strategies()`
  в воркере прогон погибает с "Unknown strategy").
Стандартный блок проверки живости и прогресса (выполняется в отдельном терминале, файлов не создаёт):
tail -n 20 <reports-dir>/log.txt
for b in <список книг/стадий>; do printf "%s: " "$b"; ls <cache-dir>/$b 2>/dev/null | wc -l; done
PID=$(cat <reports-dir>/run.pid); kill -0 "$PID" 2>/dev/null && echo "ALIVE pid=$PID" || echo "DEAD (прогон завершился или упал)"
Интерпретация: счётчики кэша растут до числа единиц работы; ALIVE и растущие счётчики = прогон здоров;
ALIVE и стоящие счётчики = проверить CPU процесса (~+1 сек ядра на 1 сек wall = считает, не завис);
DEAD без строки завершения в логе = краш: причина в хвосте лога, перезапуск тем же скриптом —
кэш сохранит прогресс.
Референс-реализация: `analytics/issue-147-trailing-production-parity/run.py` (задача #147) —
detached-прогон, кэш `cache/<book>/<TICKER>.json`, `--workers`, guard по PID-файлу.

## ⛔ Красные линии (мгновенный Reject)

1. Правка кода без сбора контекста.
2. Хардкод тикеров/параметров вне `trading_config.py` / `trading_universe`.
3. Изменение логики `StrategyEvaluator` без бит-в-бит регрессионного теста (`regression_match: true`).
4. Отсутствие проверки размера файла (`wc -c`) после heredoc.
5. Необновление `project-context.md` / `project-context.ru.md` после Issues, меняющих архитектуру/API/схему/пайплайн.
6. Начало правок БЕЗ скриптового сбора контекста (даже для single-element задач).
7. Выполнение Issue одним шагом без декомпозиции и плана в `issue-context.md`.
8. Отсутствие папки `reports/<NNN>-<branch-name>/` или отсутствие `issue-context.md` в ней.
9. Отсутствие `report.md` в артефактах задачи.

Длительный прогон (>10 мин) в attached-режиме, без PID-файла, возобновляемого кэша и воркеров — или приёмка такого прогона без проверки живости стандартным монитор-блоком.
Любая задача, не следующая этому SOP, будет возвращена на доработку без код-ревью.
