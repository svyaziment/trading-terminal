# Передача дел: как вести этот проект

Для замещающей сессии, нового агента или человека, который подхватывает работу с нуля.
Порядок чтения: этот файл, затем docs/project-context.ru.md, затем docs/maintenance/documentation-policy.md, затем docs/roadmap/development-plan.ru.md. Этот файл говорит, КАК себя вести и КУДА смотреть; он не дублирует знания из тех файлов.

## 0. За 30 секунд

Trading Terminal — это AI-ассистированная платформа аналитики и алгоритмической торговли на MOEX, интегрированная с T-Bank / Tinkoff Invest API через SDK t-tech-investments. Стек: Python 3.12 + FastAPI (бэкенд), PostgreSQL (аналитическая схема trading, будущая операционная схема terminal), React 18 + TypeScript + Vite + Tailwind (фронтенд), Docker Compose, локальный агентный слой Ollama.

Единственное не подлежащее обсуждению правило: только sandbox. Production-торговля отключена. Реальные ордера не исполняются, пока не появятся явные риск-контролы и одобрение человека. Это перевешивает любую задачу, любой shortcut и любое «так было бы быстрее».

## 1. Как работать с пользователем

Это самый важный раздел, потому что его нельзя восстановить из кода.

Будь честен, а не покладлив. Пользователь ценит взвешенное мнение и явные возражения. Если что-то неверно, преждевременно или содержит скрытую ловушку — скажи об этом с причиной. Лесть читается как утрата доверия.

Различай режим запроса. Когда пользователь говорит «давай порассуждаем» или «что думаешь» — отвечай мыслью, а не стеной кода. Когда говорит «сделай» или «вернёмся к протоколу» — выдавай task-скрипт. Не вываливай код в обсуждение и не философствуй, когда просят действие.

Предлагай выбор, а не единственный указ. Пользователь любит два-три варианта с плюсами и минусами, плюс твою рекомендацию, плюс явное «скажи "по умолчанию" — возьму твои дефолты». Этот паттерн уважает его контроль и экономит раунды.

Язык: с пользователем в чате — по-русски; агентские документы — на английском, с русскими параллелями там, где документ обращён и к человеку (см. политику документации).

Не раздувай. Плотный ответ с конкретикой лучше длинного. Пользователь устал от воды.

Признавай ошибки коротко и иди дальше. «Я был неправ в X, потому что Y» — достаточно; без самобичевания.

Не добавляй объём без просьбы. Не создавай ветку, файл, абстракцию или инфраструктурную штуку, которую пользователь не запрашивал. Если считаешь, что нужно — предложи как опцию.

## 2. Протокол разработки

Работа идёт задачами. Каждая задача — bash-скрипт в scripts/task-NNN-*.sh, который создаёт reports/<task_id>/ с report.json, report.md и log.txt. report.json — основной канал обратной связи; его статус — один из success, failed, needs_human. Всегда читай свежий report.json, прежде чем предлагать следующий шаг.

Пользователь создаёт pull request и мержит вручную. Не создавай feature-ветки, не коммить, не пушь, не открывай PR, если пользователь явно не попросил об этом в данной задаче. Несколько ранних задач, пытавшихся автоматизировать git add или push, падали или создавали трение; рабочее соглашение такое: скрипт создаёт файлы и отчёт, а git делает пользователь.

Ручные правки допустимы. Пользователь иногда правит фронтенд-файлы руками и проверяет в браузере. Контекст таких правок отслеживается по git-состоянию файлов, а не по отчётам задач; ручная правка не требует отчёта, чтобы быть «настоящей».

## 3. Куда смотреть и повторяющиеся ловушки

Полную карту файлов, модель данных, baseline API и текущие цифры читай в docs/project-context.ru.md. Не доверяй цифрам в этом handover; сверяй их с project-context и свежим reports/task-*/db_schema.md. Ловушки ниже перечислены прямо здесь, потому что замещающий агент натыкается на них в первый же день и не должен искать их по ссылкам:

backend/app/api/signals.py — легаси-роутер, он НЕ зарегистрирован в backend/app/main.py. Живые роуты — из backend/app/api/market_data.py. Не включай и не «чини» signals.py без явной задачи; сначала проверь.

Настоящие signal engine и база паттернов — в backend/app/analytics/signal_engine.py и backend/app/analytics/patterns/base.py. Сканер проекта сообщает, что backend/app/analytics/signal_patterns/engine.py и signal_patterns/base.py отсутствуют как важные файлы; это ложные срабатывания от старой раскладки. Не создавай их, если только намеренно не рефакторишь раскладку модулей.

Импорты используют app.*, никогда src.*. Форма src.* — остаток от старого проекта AlgoTerminal, и если она встречается — это баг.

Пароль базы данных берётся только из переменных окружения (PSTGRS_PWD / POSTGRES_PASSWORD). Никогда не читай, не печатай, не логируй и не коммить его.

1d-сигналов нет, потому что 1d-индикаторов мало (всего несколько сотен строк) — недостаточно для длинных скользящих средних. Это известный открытый диагностический пункт, а не регрессия.

Production-сборка фронтенда не верифицирована на момент написания этого handover. Трактуй «фронтенд работает» как «dev-сервер наблюдался», а не «сборка проходит».

## 4. Принципы решений

Честность прежде всего, как в разделе 1.

Разделяй ось git и ось агентского контекста. Хранится ли файл в git и подаётся ли его тело агенту — два независимых решения; не схлопывай их (см. политику документации, раздел 9).

Документация описывает результаты и решения, а не процесс. Если хочется написать «мы пробовали X, потом Y, потом Z» — остановись и напиши решение, которое выжило.

Контекст инкрементален. Обновляй затронутый срез, никогда не пересобирай весь снапшот. Тела файлов тяни по запросу.

Не автоматизируй преждевременно. Детерминированный скрипт, запускаемый руками, лучше хрупкого фонового демона, которого не видно.

Sandbox, идемпотентность, секреты в env. Каждая операция с данными должна быть безопасна для повторного запуска; каждый секрет остаётся в окружении.

## 10. Операционные грабли (Windows / Git Bash / Docker)

Выстраданные уроки task-035..task-046. Замещающий агент НАТКНЁТСЯ на них в первый же день. Они специфичны для окружения (Windows + Git Bash + Docker Desktop) и не очевидны из кода.

1. MSYS-конвертация ломает абсолютные posix-пути.
   Нативный Windows-python и `docker compose cp` коверкают пути вида `/f/GIT/...` в `F:\f\GIT\...` (обрати внимание на удвоенную `f`) → FileNotFoundError.
   Правило: пиши файлы ОТНОСИТЕЛЬНЫМИ путями (`Path("reports") / task_id / ...`); никогда не передавай абсолютные posix-пути в python через переменные окружения. Bash сам обрабатывает `/f/...` нормально для своих редиректов; поломка возникает, когда путь получает нативная (не-MSYS) программа.

2. `git add -A` НЕ должен использовать pathspec exclude для игнорируемых файлов.
   `git add -A -- . :(exclude)reports ...` падает с «The following paths are ignored by one of your .gitignore files», потому что pathspec-magic заставляет git явно рассматривать игнорируемые файлы.
   Правило: используй чистый `git add -A` (без pathspec). Он уважает `.gitignore` и не пытается добавить игнорируемые файлы. Убедись, что `.gitignore` покрывает `.env`, `frontend/node_modules/`, `frontend/dist/`, `reports/`, `logs/`, `backend/certs/*.pem`, `*.log`, `__pycache__/`, `*.pyc`.

3. Передавай код в контейнер через stdin, а не `docker compose cp`.
   `docker compose cp <host-путь> <контейнер>:/tmp/...` ломается на host-пути (та же MSYS-проблема).
   Правило: гони код через stdin: `printf '%s' "$CODE" | docker compose exec -T backend python -` (или `cat script.py | docker compose exec -T backend python -`). Ни один путь не пересекает MSYS-границу.

4. Пересобирай образ бэкенда после ЛЮБОГО изменения backend-кода.
   Контейнер бэкенда работает из собранного образа (нет volume-монтирования исходников для `backend`). Правка `backend/app/**` на хосте НЕ влияет на работающий контейнер, пока не пересоберёшь.
   Правило: после любого изменения бэкенда выполни `docker compose up -d --build backend` и дождись `/health`. Задача, которая правит backend-код, но пропускает пересборку, рапортует success, пока контейнер крутит старый код (так было в task-041: отчёт сказал success, но `import app.api.signals_jobs` упал внутри контейнера). Делай проверку импорта внутри контейнера ЖЁСТКИМ гейтом, а не best-effort.

5. `docker exec -T` невалиден; только `docker compose exec -T` принимает `-T`.
   У чистого `docker exec` нет флага `-T` (ошибка «unknown shorthand flag: 'T'»). Для stdin в чистый `docker exec` используй `-i` (`docker exec -i container python -`).
   Правило: предпочитай `docker compose exec -T backend ...`; если вынужден использовать чистый `docker exec` — `-i`, не `-T`.

Бонус — идемпотентность данных (выучено в task-045/046):
- Агрегация в `candles_aggregator` должна быть идемпотентным upsert: `ON CONFLICT (ticker, timestamp, timeframe) DO UPDATE`. Чистый `delete-range + insert` здесь НЕ идемпотентен, потому что (a) bucket-выражение для 4h содержит литеральный `%`, который надо экранировать как `%%` для позиционных параметров psycopg2, и (b) `figi` НЕ должен быть в `GROUP BY` (PK = `(ticker, timestamp, timeframe)`), иначе получаются дубли строк. Бери `figi` как `(array_agg(figi ORDER BY timestamp DESC))[1]`.
