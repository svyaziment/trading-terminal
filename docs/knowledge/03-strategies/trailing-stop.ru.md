## 17. Аналитика ступенчатого трейлинг-стопа (задача #139)

`analytics/issue-139-trailing-stop-new-level/` — аналитический A/B в портфельном
симуляторе 50k / 10k / max 5 / приоритет по объёму / GAME OVER: базовый фиксированный
стоп/тейк 1:3 (**A**) против того же входа со ступенчатым трейлинг-стопом (**B**) на
locked `test_20260830_new_level` (id=126, RR 1:3, SHA `dfc855195ade…`). Единственное
различие — выход; вход, начальный риск 1R, комиссия 0.06%, slippage 0 и вселенная 28
имён из `run_params.tickers` идентичны. Полный период `2024-08-01` … `timestamp <
2026-08-21` (не экспресс-окно).

Трейлинг — отдельный режим выхода в `trailing.py` (`DEFAULT_STEPS`, конфигурируемый
список `{"trigger": <R>, "stop": <R>}`; по умолчанию +2R→+1.5R, +2.5R→+2R). Ступени в R
от входа, без % хардкода. Тейк не меняется, трейлинг лишь поджимает стоп на поздней фазе,
поэтому выход по трейлингу никогда не позже базового. Модель заполнения совпадает с
`StrategyEvaluator.on_bar` (стоп раньше тейка в баре; ступень от high текущего бара
действует только на следующий бар). Модуль НЕ входит в `StrategyEvaluator`,
`portfolio_simulator.py`, бумагу или песочницу.

`extract_inputs.py` прогоняет единый «мозг» по 1-мин свечам (входы идентичны боевому
бэктесту), считает оба исхода на одном intra-trade пути и возвращает
`baseline_replay_mismatches` (обязано быть 0). БД только читается (свечи, 4h уровни,
сигналы), сделки не пишутся, четыре защищённые строки (126/36/102/118) сверяются до и
после; прогон возобновляемый через кэш по тикерам в
`reports/Vulpec/139_trailing-stop-new-level/cache/`. Пути цен остаются в памяти;
`results.json` хранит только компактные исходы A/B на сделку, поэтому `analysis.py` делает
слот-реплей, сравнение, `summary.json` и `report.md` (RU+EN) БЕЗ БД. Точные цифры A/B и
рекомендация — в `summary.json` / `report.md`. Замечание: #129/#130 считали RR 1:2
(`3b7864c4…`); #139 снимает заново под RR 1:3 — книга кандидатов #129 не переиспользуется.

## 19. Ступенчатый трейлинг-стоп в боевом пути (задача #145, эпик #142)

`backend/app/analytics/trailing_stop.py` — единственная лестница. Её вызывает каждый контур,
который закрывает позицию, поэтому конвенция заполнения не может разойтись между одиночным
бэктестом, Lab-реплеем плагина, портфельным симулятором и walk-forward; тот же модуль переиспользуют
paper (#148) и песочница live (#151).

- **Чистая функция шага.** `ladder_stop(entry_exec, initial_stop, steps, ref_high)` возвращает
  `(stop_price, step_reached)`: верхнюю ступень, чей триггер `entry_exec + trigger × R` достигнут
  максимумом цены `ref_high`, где `R = entry_exec - initial_stop`. Цены выводятся из входа и
  начального риска — процентов в движке нет. `TrailingState.evaluate(high, low, bar_key)`
  превращает это в решение по бару, а `evaluate_bar(state, ...)` — единственный вызов контуров.
- **Порядок внутри бара и есть контракт.** (1) `low <= live_stop` → выход по `live_stop` с причиной
  `trailing`, если лестница уже поджимала стоп, и обычным `stop`, если ещё нет; (2) иначе
  `high >= take` → выход по тейку; (3) только если ничего не сработало, вооружить следующую ступень
  по high **этого** бара — действовать она начнёт со **следующего**. Тейк не двигается, стоп не
  опускается и не оказывается ниже начального. Это сознательный перенос конвенции #139
  (`analytics/issue-139-trailing-stop-new-level/trailing.py`): расхождение завалит гейт паритета
  #147.
- **Вооружение привязано к бару.** Движок использует `idx`, плагин — `context.timestamp`. Повторная
  подача того же бара — no-op, и именно поэтому жизненный цикл плагина (`manage_position` перед
  `check_exit`) не даёт intra-bar look-ahead.
- **Геометрия входа живёт в позиции.** `position['initial_stop']`, `['risk_r']`,
  `['trailing_steps']`, `['stop']` / `['current_stop']` и `['step_reached']` отражают лестницу.
  `stop` / `step_reached` — пара, которая станет действующей со следующего бара, а
  `position['trailing_state'].live_stop` — стоп, по которому выходил текущий бар. `step_reached`
  доезжает до записи сделки и до портфельной книги; состояние создаётся на позицию, и каждое окно
  walk-forward открывает свой evaluator — между окнами память не течёт.
- **Выключено по умолчанию, fail-safe при мусоре.** `trailing_from_config()` возвращает None — «веди
  эту позицию ровно как до #145» — если ключа нет, `enabled=false`, лестница пуста или
  `resolve_trailing_stop()['reasons']` непустой. Движок не бросает исключений: отказывать при записи
  — работа #146 (редактор Lab) и #149 (API), а до них битый блок меняет только лог.
- **Имена причин.** Прод эмитит `stop` / `take` / `trailing`; аналитические книги #139/#143
  использовали `initial_stop` / `take` / `trailing`. Отображение зафиксировано в
  `reports/Arctic/145_trailing-evaluator/grid_check.py` (`EXIT_REASON_MAP`), формальный гейт — за
  #147.
- **Метрики.** `_portfolio_metrics` сохраняет все прежние ключи и добавляет `exit_reason_counts`,
  `trailing_exits`, `take_exits`, `initial_stop_exits` и `trailing_exit_share_pct`.
- **Как воспроизвести.** Матрица поведения: `cd backend && python -m pytest -q
  tests/test_trailing_stop.py tests/test_trailing_contract.py`. Регрессия бит-в-бит на
  locked-конфигах (только чтение, нужно хранилище): на этой ветке
  `python reports/Arctic/145_trailing-evaluator/regression_run.py --label after --out after.json`;
  на `main` — тот же скрипт с `--label baseline --backend <worktree-main>/backend --out
  baseline.json`; затем `python reports/Arctic/145_trailing-evaluator/regression_run.py --compare
  baseline.json after.json --verdict regression_verdict.json` → `regression_match: true`.
  Направленная проверка лестницы по опубликованной книге #143 (офлайн, на кэшах путей):
  `python reports/Arctic/145_trailing-evaluator/grid_check.py`.
- **Выбор сетки эта задача не меняет:** боевой дефолт остаётся `ultra_late_tight` (§18, handover
  §35), а `ref139` дефолтом не является — это якорь паритета, который #147 инжектирует явно.
- **Вне объёма #145:** paper (#148), гейт записи в Lab / API (#146 / #149), панели Paper/Live
  (#150), песочница live (#151), гейт паритета (#147) и приёмочный вердикт на живом периоде (#152).

## 20. Редактор трейлинг-стопа в Strategy Lab (задача #146, эпик #142)

  уровня**; превращение его в параметр `levels_reversal` сломало бы и схему-дрессер, и контракт #144.
- Полностью schema-driven, без запасного варианта на фронте. Секция появляется только после ответа
  `GET /api/strategies/trailing-schema`, и все дефолты, границы, `max_steps`, разрешение ввода
  `0.1R`, **имя утверждённой сетки и её ступени**, а также словарь кодов причин приходят из этого
  ответа — его формирует `trading_config.get_trailing_stop_schema()` прямо из `TRAILING_STOP`,
  который не мутирует. Если endpoint недоступен, секции просто нет — устаревший бандл не сможет
  предложить неутверждённую лестницу.
  Долгосрочная форма endpoint за #149, и он **наследует этот** — расширять нужно функцию, а не
  плодить второй объект схемы в роутере.
- Вся логика (разбор, `validateLadder`, сборка payload) — в `frontend/src/trailingStop.ts`, чистыми
  функциями; `TrailingStopFields.tsx` только рисует и чисел трейлинга не содержит. Именно это
  разделение делает критерий «нулевой хардкод в TSX» проверяемым. `validateLadder` повторяет
  `validate_trailing_steps()` (#144) ступень за ступенью, включая строгий `min_trigger`, молчаливое
  сворачивание точных дубликатов и проверку границ даже при выключенном переключателе.
- Два поведения, которые важно знать до правки:
  - **Нетронутое остаётся нетронутым.** Сборщик payload возвращает `null`, пока редактор не
    трогали, а `config`-мемо раскладывает блок условно — поэтому стратегия без `trailing_stop`
    по-прежнему сохраняется без ключа. Но если блок трогали и сохранить с выключенным
    переключателем, в БД уедит явный `enabled: false`: отказ от трейлинга — это мнение, отсутствие
    ключа — нет.
  - **Лестница обязана быть управляемым строковым состоянием с `step=0.1`.** Утверждённая сетка
    `ultra_late_tight` — `2.0→1.9 / 2.5→2.4 / 3.0→2.9` с зазором 0.1R; округление браузером до
    0.5R незаметно превратило бы 1.9 в 2.0, и Lab начала бы отправлять лестницу, которую #144
    отвергает. Round-trip покрыт тестами.
- Таблица сделок теперь рисует полное замкнутое множество причин движка
  (`stop, take, trailing, holding, signal, session`) из `frontend/src/exitReasons.ts`. До #146
  колонка была бинарной тейк/стоп, поэтому каждый выход `trailing` подписывался «стоп» — работа
  лестницы неотличалась от выбивания по начальному стопу.
- **Гейта по-прежнему нет:** сохранение через API не вызывает `require_valid_trailing_stop()` —
  валидация на записи с 422 относится к #149, так что клиентскую проверку можно обойти клиентом
  кроме Lab. Страховкой остаётся движок #145: он не вооружает отвергнутую лестницу.
- **`config_hash` в этом репозитории не существует** — проверка «хеш меняется после включения» из
  требования 4 здесь непроверяема; по сути ей соответствует то, что сохраняемый JSONB `config`
  действительно несёт блок. Операционные детали: handover §38.

## 21. Live trailing stop (Задача #151)

Завершена 2026-09-16. Live/sandbox trailing-stop с храповиком, безопасностью рестарта и kill-switch.

**Архитектура**:
- **Армирование**: При открытии позиции (`process_signal`), если `strategy_config.trailing_stop.enabled=true` и kill switch выключен, executor армит трейлинг с 0 брокерских вызовов. Параметры: `trailing_enabled=true`, `trailing_steps` (JSON), `risk_r=entry-stop`, `current_stop_price=stop_price`, `step_reached=0`.
- **Храповик**: `monitor_positions()` вызывает `_apply_trailing(row, current_price)` для каждой активной позиции. Восстанавливает `TrailingState` из колонок БД, вычисляет текущую цену как одиночный бар, условный UPDATE `WHERE id=%s AND step_reached < %s` обеспечивает монотонность.
- **Выход**: Когда `current_price <= current_stop_price`, отменяет take, выставляет sell-limit по текущей цене. Записывает `exit_price_model` (цена стопа), `exit_price_actual` (цена исполнения), `slippage_bp`, `slippage_r`, `lots_executed`. Статус `closed_trailing`, причина `trailing`.
- **Kill switch**: `_refresh_kill_switch()` читает `trading.app_settings.trailing_kill_switch` перед каждым циклом мониторинга. ON приостанавливает арминг/храповик; armed-позиции сохраняют состояние. Fail-safe: ошибка БД → kill switch ON.
- **Advisory lock**: `pg_try_advisory_lock(151001)` в `initialize()`, освобождение в `shutdown()`. Предотвращает запуск нескольких экземпляров.
- **Безопасность рестарта**: Состояние восстанавливается из колонок БД; in-memory состояния нет. Идемпотентный replay.

**База данных**:
- Миграция `20260916_001_live_trailing_runtime.py`: расширяет `live_positions.status` CHECK до `closed_trailing`, `closed_broker`; добавляет `exit_price_model`, `exit_price_actual`, `slippage_bp`, `slippage_r`, `lots_executed`; создаёт таблицу `trading.app_settings`.
- Колонки `trailing_enabled`, `trailing_steps`, `risk_r`, `current_stop_price`, `step_reached` уже существуют (миграция `20260915_002`).

**Конфигурация**:
- `LIVE_TRADING.trailing_kill_switch`: по умолчанию `false`, runtime-override через `trading.app_settings`.
- `LIVE_TRADING.live_trailing_enabled`: по умолчанию `true`, глобальный переключатель.
- `LIVE_TRADING.trailing_protective_ticks`: по умолчанию `5`, защитный отступ для исполнения стопа.
- `LIVE_TRADING.trailing_ticker_allowlist`: по умолчанию `[]`, опциональный фильтр тикеров.

**Тестирование**: 68 тестов в `test_live_executor.py` (43 новых для #151). Покрытие: арминг, храповик, монотонность, kill switch, факты исполнения, слиппедж, rate limiter, валидация конфига.

**Эксплуатация**: См. `docs/strategy/live-trading.ru.md` для пользовательской документации, handover §41 для операционных деталей.

## 36. Эксплуатация контракта конфигурации трейлинг-стопа (задача #144)

- `config.trailing_stop` — полноценный ключ `strategies.config` (JSONB, без миграции схемы):
  `{"enabled": bool, "steps": [{"trigger": 2.0, "stop": 1.9}, ...]}` — оба числа это множители R от цены
  входа. **`take_partial` в этом контракте нет**, как и в именовании `trigger_r` / `lock_r`: частичный выход
  не входил в утверждённую сетку `ultra_late_tight`, поэтому #144 его не выдумывает.
- Контракт живёт в `backend/app/analytics/trading_config.py`: `TRAILING_STOP` (дефолты + границы),
  `get_trailing_stop_config()`, `normalize_trailing_stop()`, `validate_trailing_steps()`,
  `resolve_trailing_stop()` и `require_valid_trailing_stop()`. `validate_trailing_steps()` не бросает
  исключений и не меняет входные данные — она возвращает отсортированный набор **стабильных кодов причин**
  (`trailing_disabled`, `trailing_step_invalid`, `trailing_not_monotonic`, `trailing_too_many_steps`);
  пустой список означает «принято». Переименование кода — разрыв контракта: #149 отдаёт эти строки как есть,
  а `require_valid_trailing_stop()` — единственный хелпер, который превращает их в `ValueError`.
- Границы читаются из `TRAILING_STOP` и являются единственным источником истины (движок, API и фронтенд не
  имеют права их дублировать): `0 < trigger <= 3.5` (`min_trigger` — строгая граница, поэтому шаг на 0R не
  шаг), `0 <= stop <= 3.0`, всегда `stop < trigger`, не больше `max_steps` = 6 ступеней. Шаг — это **dict с
  конечными числами `trigger` и `stop`**: `bool` числом не считается, список пар `[trigger, stop]` **не**
  принимается, других написаний ключей-алиасов нет. Стоп не может снижаться по мере роста триггера
  (`trailing_not_monotonic`), одинаковый триггер с двумя разными стопами — тоже `trailing_not_monotonic`, а
  ровно повторяющаяся пара убирается нормализацией и ошибкой не считается. **Минимального зазора** между
  триггером и стопом нет намеренно: боевая лестница стоит на 0.1R, поэтому эвристика «зазор ≥ 0.5R»
  отвергла бы поставляемый дефолт.
- `resolve_trailing_stop(config)` — единичная точка входа для потребителей: `{"enabled", "steps",
  "reasons"}`. Отсутствие ключа, `None`, `{}` и не-dict-блок разрешаются в
  `{"enabled": false, "steps": [], "reasons": []}` — именно поэтому конфиги без ключа ведут себя ровно как
  до #144. Флаг `enabled` строгий: лестницу включают только настоящий `bool` либо строки
  `'1' / 'true' / 'yes' / 'on'`, любое другое truthy-значение нормализуется в `false`.
  `normalize_trailing_stop()` идемпотентна, сохраняет точность float (1.9 / 2.4 / 2.9 не округляются до
  0.5R), сортирует по `(trigger, stop)` и выбрасывает структурно битые шаги: это канонизатор, **а не**
  gatekeeper, поэтому проверять нужно исходный список.
- Дефолт `TRAILING_STOP`: `enabled=false`, шаги `2.0→1.9 / 2.5→2.4 / 3.0→2.9` — сетка
  `ultra_late_tight` из §35 — с дефолтами границ `max_steps=6`, `min_trigger=0.0` (строгая),
  `max_trigger=3.5`, `min_stop=0.0`, `max_stop=3.0`. Сама правка лестницы ничего не включает.
- **Применяется с #145 — гейта на записи по-прежнему нет.** `validate_config()` **не существует в этом
  репозитории**, поэтому при создании/обновлении стратегии и при запуске Lab битая лестница по-прежнему
  принимается: блок `enabled=true` без пригодных шагов сохраняется и просто отдаёт `trailing_disabled`.
  Гейт, который должен вызвать #149, остаётся `require_valid_trailing_stop()` — #146 отдал
  редактор Lab без него (§38): редактор проверяет лестницу на клиенте теми же кодами, но POST
  битой конфигурации по-прежнему проходит. В #145 изменилась

## 41. Эксплуатация live trailing stop (задача #151)

Завершена 2026-09-16. Live/sandbox trailing-stop с храповиком, рестартом и kill-switch.

### Обзор архитектуры

- **Армирование**: `process_signal()` армит трейлинг при открытии позиции, если `strategy_config.trailing_stop.enabled=true` и kill switch выключен. Ноль брокерских вызовов. Параметры записываются в `trading.live_positions`: `trailing_enabled=true`, `trailing_steps` (JSONB), `risk_r=entry-stop`, `current_stop_price=stop_price`, `step_reached=0`.
- **Храповик**: `monitor_positions()` вызывает `_apply_trailing(row, current_price)` для каждой активной позиции с `trailing_enabled=true`. Восстанавливает `TrailingState` из БД, вычисляет текущую цену как одиночный бар, условный UPDATE `WHERE id=%s AND step_reached < %s` обеспечивает монотонность.
- **Выход**: Когда `current_price <= current_stop_price`, отменяет take, выставляет sell-limit по текущей цене (blocking=False, откладывается при исчерпании rate limit). Записывает `exit_price_model`, `exit_price_actual`, `slippage_bp`, `slippage_r`, `lots_executed`. Статус `closed_trailing`, причина `trailing`.
- **Брокерский amend (задача #175)**: каждый шаг храповика дополнительно переносит брокерский `STOP_LOSS` через дублирование — `post_stop_order()` для нового стопа, `get_stop_orders()` для подтверждения, затем `cancel_stop_order()` для старого, более низкого. Храповик в БД сохраняется даже при сбое amend (стоп никогда не опускается), следующий цикл повторяет попытку; сбой пишет `trailing_amend_failed`, неподтверждённый новый стоп — `trailing_amend_unverified` с постановкой старого в очередь `_cancel_pending_stops()`.
- **Kill switch**: `_refresh_kill_switch()` читает `trading.app_settings.trailing_kill_switch` перед каждым циклом мониторинга. ON приостанавливает арминг/храповик; armed-позиции сохраняют состояние. Fail-safe: ошибка БД → kill switch ON.
- **Advisory lock**: `pg_try_advisory_lock(151001)` в `initialize()`, освобождение в `shutdown()`. Предотвращает запуск нескольких экземпляров.
- **Безопасность рестарта**: Состояние восстанавливается из колонок БД; in-memory состояния нет. Идемпотентный replay.

### База данных

- Миграция `20260916_001_live_trailing_runtime.py`: расширяет `live_positions.status` CHECK до `closed_trailing`, `closed_broker`; добавляет `exit_price_model`, `exit_price_actual`, `slippage_bp`, `slippage_r`, `lots_executed`; создаёт таблицу `trading.app_settings`.
- Колонки `trailing_enabled`, `trailing_steps`, `risk_r`, `current_stop_price`, `step_reached` уже существуют (миграция `20260915_002`).

### Конфигурация

- `LIVE_TRADING.trailing_kill_switch`: по умолчанию `false`, runtime-override через `trading.app_settings`.
- `LIVE_TRADING.live_trailing_enabled`: по умолчанию `true`, глобальный переключатель.
- `LIVE_TRADING.trailing_protective_ticks`: по умолчанию `5`, защитный отступ в тиках `min_price_increment` между триггером брокерского стопа и лимитной ценой, которую он активирует (задача #175).
- `LIVE_TRADING.trailing_ticker_allowlist`: по умолчанию `[]`, опциональный фильтр тикеров.
- `LIVE_TRADING.broker_stop_enabled`: по умолчанию `true`; `false` отключает постановку брокерского `STOP_LOSS` и оставляет только синтетический fallback (задача #175, отладочный переключатель).
- `LIVE_TRADING.protection_retry_seconds`: по умолчанию `30`, база экспоненциального backoff после неудачного `PostStopOrder`.

- `LIVE_TRADING.operations_lookback_hours`: по умолчанию `24`, окно `GetOperations` для сверки филлов.
